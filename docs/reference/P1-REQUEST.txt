==================================================
IN SCOPE
==================================================

Implement:

MEDICINE CATALOG

The system must persist structured medicine products.

Support fields where justified by available data, such as:

- product_id
- brand_name
- generic / active ingredient
- strength
- dosage_form
- route
- release_type
- manufacturer
- pack/presentation information
- source
- source URL/reference

- collected/imported date
- review/import status

Do not require every field if the source does not provide it.

Use strong database constraints where appropriate.

==================================================
PRODUCT IDENTITY
==================================================

This is critical.

A medicine must NOT be identified only by its brand name.

Different presentations must remain distinct.

For example:

Medicine X 250 mg tablet

and

Medicine X 500 mg tablet

must NOT be the same product row.

Likewise:

Medicine X tablet

and

Medicine X suspension

must remain distinguishable.

Design product identity so future search can safely handle:

- same brand
- multiple strengths
- multiple forms
- different presentations
- possibly multiple manufacturers

Do not encode assumptions that will break when the catalog grows beyond Getz Pharma.

==================================================
CATALOG IMPORT
==================================================

Build a controlled import mechanism for qualified medicine data.

Import the existing P0 sample into PostgreSQL.

The importer must:

- validate input;
- preserve provenance;
- reject malformed records;
- avoid accidental duplicates;
- handle reruns safely;
- not silently overwrite conflicting medicine facts;
- produce clear errors.

Prefer idempotent imports where practical.

Test importing the same source more than once.

Do NOT scrape arbitrary websites just to increase medicine count during P1.

Catalog expansion may continue only from defensible sources.

==================================================
PHARMACY DOMAIN
==================================================

Implement pharmacy entities.

Support at minimum:

- pharmacy ID
- name
- address or location label
- latitude
- longitude
- active status
- account ownership
- created/updated timestamps

Demo pharmacy locations may be synthetic.

Clearly label demo data as synthetic.

Do not imply that demo pharmacies represent live real-world inventory.

==================================================
AUTHENTICATION
==================================================

Implement a simple but defensible authentication system for pharmacy users.

Requirements:

- passwords must be hashed using an established library;
- no plaintext passwords;
- no custom cryptography;
- no hardcoded credentials;
- authentication must be verified server-side;
- secrets must come from configuration/environment;
- authentication errors must not leak sensitive information.

Choose a suitable V1 approach.

Examples:

- secure server-side session authentication;
or
- another simple, well-established browser authentication mechanism.

If cookies are used, apply the relevant security protections.

Do not overengineer authentication.

==================================================
AUTHORIZATION
==================================================

This is a hard requirement.

Pharmacy A must NEVER be able to modify:

- Pharmacy B inventory
- Pharmacy B profile
- Pharmacy B stock confirmation

Authorization must be enforced by the backend.

Frontend route hiding is NOT authorization.

Create explicit negative tests.

==================================================
INVENTORY DOMAIN
==================================================

Create an inventory relationship between:

pharmacy
+
medicine product

Inventory should support at minimum:

- pharmacy_id
- product_id
- quantity or explicit stock state
- price
- currency
- stock_confirmed_at
- created_at
- updated_at
- revision/version field

Use a uniqueness constraint so a pharmacy cannot accidentally have multiple active inventory rows for the same product unless the domain model explicitly requires it.

==================================================
STOCK FRESHNESS SEMANTICS
==================================================

This must be implemented correctly now because P2 depends on it.

stock_confirmed_at means:

"The last time pharmacy staff actually confirmed this stock."

It is NOT the same as updated_at.

Changing only:

- price
- unrelated metadata
- pharmacy profile

must NOT automatically refresh stock_confirmed_at.

Only an explicit stock-confirmation action or stock update that semantically confirms stock should change it.

Document this behavior.

Test it.

==================================================
QUANTITY / STOCK VALIDATION
==================================================

Reject invalid values.

Examples:

- negative quantity
- invalid price
- invalid currency
- nonexistent product
- invalid pharmacy
- malformed coordinates

Where appropriate, enforce integrity in PostgreSQL itself, not only application code.

==================================================
PRICE
==================================================

Store price with a suitable exact numeric type.

Do NOT use floating-point storage for monetary values.

Support currency explicitly.

For V1 this will normally be PKR, but do not hardwire the schema so badly that it cannot represent currency cleanly.

==================================================
CONCURRENT UPDATE PROTECTION
==================================================

This is mandatory.

Implement optimistic concurrency or an equivalent safe mechanism.

Use a revision/version number or similar.

Example:

Client reads inventory revision 4.

Another update changes it to revision 5.

The old client must NOT silently overwrite revision 5.

The stale update should fail with a clear conflict response.

Test this behavior using real PostgreSQL.
